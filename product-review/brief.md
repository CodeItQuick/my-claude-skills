# Product Brief

A product brief is a cached description of **what this codebase is a product for**. It is generated once per repository, stored in the reviewed repository, and read at the start of every run.

Its purpose is to supply the context a diff cannot: who uses this, how it makes money, what data it holds, what surfaces it exposes. Several role profiles have suppression rules that depend on these facts — the Revenue Operations Analyst suppresses entirely on a flat-rate product, the Growth Lead suppresses on a surface with no meaningful traffic, the Launch Editor suppresses when there are no external users, and Legal Counsel needs to know whether real personal data is in play. Without a brief those rules cannot fire, and the panel over-reports.

---

## The one rule that matters

**The brief is context, never evidence.**

A brief fact may *suppress* a finding on its own. A brief fact may never *support* one. Every reported finding still requires two evidence types drawn from the diff, exactly as the evidence requirement states. A role that cites the brief in place of code has produced an opinion about the product, not a review of the change.

This applies doubly to the Inferred section below, which is model knowledge rather than observation.

---

## Location and lifecycle

**Path:** `.product-review/brief.md` in the root of the reviewed repository.

**On first run:** if no brief exists, ask the user before writing one. This creates a new file in their repository, and some teams will want it in `docs/`, checked in, or gitignored. Respect an answer that names a different path, and record that path in the run.

**On later runs:** read the existing brief. Compare its recorded commit SHA against `HEAD`. Report drift rather than silently trusting a stale file:

- Under ~100 commits and under ~90 days: use it as-is.
- Beyond either threshold: use it, but state in the run that the brief is stale and offer to regenerate. Treat every line in the Inferred section as unreliable until refreshed — competitive and category claims decay fastest.

**On `--brief`:** regenerate unconditionally, overwriting the existing file. Preserve any content under `## Human notes` verbatim; that section is written by people, not by this skill.

---

## What to inspect

Read broadly and cheaply. This is a survey, not an audit — prefer entry points and manifests over exhaustive file reading.

- **README, docs directory, marketing copy in the repo** — the product's own account of itself
- **Dependency manifest** (`package.json`, `Gemfile`, `pyproject.toml`, `go.mod`) — framework, billing SDKs, analytics, auth providers, LLM clients, email and support tooling
- **Routes, controllers, or API definitions** — the surface inventory and who can reach it
- **Models, schema, migrations** — the domain nouns, and any field carrying personal, financial, or health data
- **Auth and tenancy** — single-user, team-based, or multi-tenant; roles and permission tiers
- **Billing and plan code** — plan definitions, entitlement checks, quota enforcement, metering
- **Config and environment** — regions, third-party services, feature flag system
- **CI, deploy, and ops files** — how it ships, how often, what is automated
- **Test layout** — what is covered, which suggests what the team treats as load-bearing

## Structure of the file

Write these sections in this order. Keep the whole brief under roughly 400 words of prose — it is loaded on every run.

```markdown
# Product Brief

<!-- Generated by the product-review skill. Regenerate with --brief. -->

- **Derived from commit:** <sha>
- **Generated:** <YYYY-MM-DD>

## Derived

Facts grounded in this repository. Every line cites at least one path.

- **What it is:** [one sentence] (`path`)
- **Users and tenancy:** [who accounts belong to, roles and permission tiers] (`path`)
- **Business model:** [free, flat-rate, tiered, usage-based, none evident] (`path`)
- **Surfaces:** [web app, public API, CLI, webhooks, integrations, mobile] (`path`)
- **Sensitive data:** [personal, financial, health data present or absent; regions] (`path`)
- **Delivery:** [CI, deploy cadence, feature flag system, staged rollout capability] (`path`)
- **Maturity signals:** [test coverage shape, migration count, error handling posture] (`path`)

## Inferred

Model knowledge, not observation. **Cannot support a finding.** Verify before repeating.

- **Category:** [what class of product this is]
- **Conventional capabilities in this category:** [table stakes a serious product here offers]
- **Likely competitive set:** [named products, with the caveat below]
- **Category direction:** [where this class of product has been heading]

> These claims reflect the model's knowledge at training time and decay quickly.
> Named-competitor claims are the least reliable and must be phrased as claims to
> confirm, never as established fact.

## Unknowns

Facts the code cannot reveal. Roles must not assume these — treat each as "unknown",
not as "absent". A human can fill these in; do not invent them.

- Actual traffic volume and user counts
- Ideal customer profile and target segment
- Contractual commitments, SLAs, DPAs, certifications held
- Pricing intent and packaging strategy
- Roadmap, strategic direction, competitive priorities

## Human notes

<!-- Written by people. Preserved verbatim across regeneration. -->
```

## Writing rules

**Derived section:** every bullet cites a path. If no path supports a claim, the claim belongs in Inferred or Unknowns. Write "no billing code present" rather than omitting the line — an absence is a derived fact and it is exactly what a suppression rule needs.

**Inferred section:** name the category confidently, since category conventions are stable. Name competitors sparingly and always as claims to verify. Prefer "products in this category conventionally offer bulk export and audit logs" over "Competitor X has bulk export" — the first is durable, the second rots.

**Unknowns section:** never fill these in from inference. An empty slot is a correct answer; a plausible guess is not. If a role would need one of these facts to report a finding, that finding is suppressed.

**Tone:** flat and factual. This file is read by roles, not by people, and adjectives do nothing for it.
